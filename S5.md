Plan S4 — completar el MVP con Builder/Verifier
Estado de partida
Actualmente están implementados:
- Registro USER.
- Afiliación opcional a plan activo.
- Catálogo REST de planes.
- Frontend React/Vite conectado al registro.
- Pruebas Maven, Vitest, lint y build.
Antes de cerrar S4 todavía debe completarse el núcleo de citas de S3.
Fase 0 — Cerrar prerequisitos S3
1. Publicar catálogos restantes: sedes, especialidades y estados.
2. Implementar ADMIN:
   - CRUD de especialidades.
   - Creación y activación de profesionales.
   - Asignación de especialidades y sedes.
3. Implementar disponibilidad:
   - Bloques futuros.
   - Slots de 30 minutos.
   - Validación de solapamientos.
   - Restricción por sede y profesional activo.
4. Implementar reservas:
   - General → APPROVED.
   - Especializada → REQUESTED.
   - Bloqueo transaccional de slots.
   - Conflicto 409 para doble reserva.
5. Implementar aprobación/rechazo ADMIN.
6. Conectar frontend sin mocks.
7. Ejecutar prueba Red → Green y hook de secretos ficticios.
Fase 1 — Identidad y catálogos S4
- Login con JWT access/refresh.
- Logout y revocación de refresh token.
- Recuperación y cambio de contraseña sin SMTP obligatorio.
- Perfil USER:
  - GET /users/me.
  - Actualización únicamente de teléfono.
- CRUD ADMIN de EPS, planes y especialidades.
- Migración Flyway posterior a las migraciones existentes.
- Pruebas de autorización, ownership y errores 401/403/404/409.
Fase 2 — Ciclo de vida de citas
- GET /appointments y detalle.
- Cancelación de citas futuras.
- Liberación de slots al cancelar.
- Solicitud de reprogramación.
- Retención de nueva franja mientras está PENDING.
- Aprobación y rechazo ADMIN.
- Preservación de la cita original si se rechaza.
- Historial obligatorio de cada transición.
Fase 3 — Operación profesional
- Agenda diaria/semanal del profesional.
- Consulta únicamente de citas propias.
- Cierre de atención como:
  - COMPLETED.
  - NO_SHOW.
- Restricción por fecha, profesional y estado.
- Historial de cierre.
Loops Builder/Verifier
Loop 1 — Reprogramación guiada
Máximo 4 iteraciones.
El Builder implementa y corrige. El Verifier solo revisa:
- cita original intacta durante PENDING;
- nueva franja retenida;
- aprobación intercambia slots;
- rechazo libera la nueva franja;
- motivos obligatorios;
- pruebas backend/frontend verdes.
Loop 2 — Reconciliación cross-repo
Máximo 3 iteraciones.
Validar que:
- DTO backend y cliente REST coinciden;
- errores 403/409 se muestran correctamente;
- estados APPROVED, REQUESTED, PENDING, REJECTED son consistentes;
- la UI conserva el diseño aprobado;
- Docker funciona de extremo a extremo.
Loop 3 — Reto independiente
El reto recomendado es la doble reserva concurrente:
- dos usuarios intentan reservar el mismo slot;
- solo uno obtiene éxito;
- el segundo recibe 409;
- no quedan dos citas sobre los mismos slots.
Evidencia obligatoria
Crear evidence/s4/ con:
- loop-01-reprogramacion.md;
- loop-02-reconciliacion.md;
- loop-03-reto-independiente.md;
- resultados Maven;
- resultados Vitest, lint y build;
- pruebas Docker cross-repo;
- evidencia de hook FAIL/PASS;
- hashes de commits;
- HU, criterios de aceptación y DoD verificados.
Criterio de cierre S4
S4 se considera completado únicamente cuando:
- el MVP permite reservar, cancelar y reprogramar;
- el profesional puede gestionar agenda y cerrar citas;
- ADMIN puede gestionar catálogos y decisiones;
- todo cambio de estado tiene historial;
- los loops tienen resultado PASS;
- frontend y backend pasan sus verificaciones;
- la documentación Scrum y Wiki refleja la evidencia;
- existen commits separados en develop para ambos repositorios;
- no se hace merge a main sin autorización explícita.
